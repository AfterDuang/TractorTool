## 怎么阅读

- 首次了解项目：先读根 README；具体实现和验收状态继续查看开发与验收。
- 接续开发：按根 AGENTS.md 阅读产品需求、架构、开发与验收、开发上下文，再核对源码。
- **默认不读项目历史**。只有追查某次变更、选型依据、命令或回归时，才通过 E 编号/主题索引读取相关片段；归档 M1 不表示将历史缺证项改为通过。
- 开发或修改插件：加读[源码组织规范](PLUGIN_DEVELOPMENT.md#source-organization)及其余接入规则、`Docs/Plugins/<插件名>.md`；已有源码 README 时沿其阅读入口定位文件。首版两个插件使用相同公开 SDK；独立测试插件只是机制夹具。
- 了解“做到了什么、是否通过”：只以开发与验收中的当前状态及对应证据为准。插件文档中的设计、示例和验收方法不代表已有实现。

## 引用与依赖的查阅顺序

- **需求 → 设计 → 接入**：产品说明定义行为，架构定义框架如何实现，插件规范定义调用方必须遵守的协议；互相链接，不复制整段规则。具体插件只描述自身业务并引用公共规范。
- **源码与版本**：工程引用和 NuGet 依赖以各 `.csproj` 为准；SDK 工具链见 `global.json`，产品版本见 `Directory.Build.props`，接口版本见公开 API 定义，插件身份与外部工具资料见 `plugin.json`。解决方案分组不建立程序集依赖。
- **依赖分类**：[架构分层](ARCHITECTURE.md#1-当前代码与目标结构)解释工程依赖方向；[插件依赖表](PLUGIN_DEVELOPMENT.md#dependency-kinds)区分 .NET 运行时、共享 SDK、私有库和外部工具；[脚本说明](../scripts/README.md)解释构建工具及许可收集边界。
- **状态 → 证据**：开发台账链接具体历史记录，交接只摘录当前约束和下一步；历史可以说明旧方案，不能成为当前规则的唯一入口。参考项目、截图与调研放历史，不扩充日常必读链。

## 怎么维护

1. 宿主需求变更写产品需求；公共结构和服务边界变更写架构；跨插件接入规则变更写插件规范；具体业务变更只写对应插件文档。
2. 保留需求 R、验收 A 和证据 E 编号。当前验收状态只写 DEVELOPMENT.md，历史执行详情只写 PROJECT_HISTORY.md；产品中的插件条目仍是范围索引。
3. 实质性进展替换 DEVELOPMENT.md 的当前摘要、更新验收状态，再刷新 PROJECT_CONTEXT.md。交接只保留当前边界、关键入口和下一步，不复制整个架构或验收表；插件详细验收方法链接到对应文档。已完成的轮次归历史并链接，同轮后续 Review 归回对应 E 编号；未关闭问题、仍有效约束及当前操作入口不得只留在归档。本地产物快照只维护在 [开发台账](DEVELOPMENT.md#local-artifacts)，注明观察范围；旧路径不继续充当现行入口，文件存在不代替校验或运行证据。
4. 新增正式插件时，在 Docs/Plugins 下建立一份文档，包含范围、需求、宿主依赖、内部设计、错误边界与验收方法，并从本页链接。不另建插件专属的 Agent 指令入口。
5. 用户新指示优先于旧文档；整理结构不能删减已确认语义，不能将待验证方案改写成已实现。
6. 跨文档链接优先使用稳定锚点；改标题时检查反向引用。源码路径与本地锚点做静态核对，外部链接、构建和运行是否验证分别报告，不以链接存在推定内容仍然有效。
